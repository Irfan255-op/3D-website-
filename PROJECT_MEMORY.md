# Project Memory — shaikh.labs

Read this before touching `resources/js/app.js` or `resources/views/home.blade.php`. The hero sphere system especially carries a lot of decisions that aren't obvious from the code alone — this file exists so a new session (or a future me) doesn't have to re-derive them or repeat a dead end already walked into once.

**Update this file after every change that affects the hero sphere, homepage structure, or brand system** — not every tiny CSS tweak, but anything a future session would otherwise have to re-discover by reading a diff or asking the user again. Keep the changelog append-only (newest entry on top), and keep the "Current state" section in sync with reality, not with what was *intended* — if something was tried and reverted, say so and say why, don't just delete the trace.

## Current state — homepage (`resources/views/home.blade.php`)

Sidebar shell (`resources/views/layouts/app.blade.php`): fixed left **icon rail**, `5rem`/80px wide on desktop (`lg:w-20` / `lg:pl-20` — was a 256px text-link sidebar, `16rem`/`lg:w-64`, narrowed per user request), mobile falls back to a top navbar below `lg` (unchanged, still full text labels in a hamburger menu).

Six sections, each a translucent `.stage-card` on one side of the viewport with the WebGL sphere on the other (card side alternates via `data-side="right"`):

| # | Section | Card side | Central object | Card component |
|---|---|---|---|---|
| 1 | Hero `#top` | left (text) | smooth pearl-pink orb (hover-reactive) | staged intro, status dot, scroll cue |
| 2 | About `#about` | right | orb, **soft rolling waves** (`data-sphere-spike="1"`) + Motion spring bloom | bio |
| 3 | Services `#services` | left | orb + **tech-stack text bands** wrapped around it (`data-sphere-bands="1"`) | **exclusive `<details>` accordion** |

(The `gem`/`discs` attribute names are historical — they've driven three successive designs each; the names were never worth the churn of renaming.)

The sphere's per-section target (position, scale, rotation, spike, bands, fade, gem, discs, beacon) comes from `data-sphere-*` attributes read in `measureWaypoints()` in `app.js`, re-measured live from the DOM (not baked into fixed scroll percentages) so it stays correct across resizes and content changes. A dwell/ease curve (`segmentEase`, `DWELL = 0.28`) holds the sphere at each waypoint's pose while that section is being read, rather than drifting the whole time.

**Sphere material (current)**: pearl-pink (`uColorA/B/C` `#e8a0bc/#f5c2d6/#f29bc4`), near-opaque (`glassAlpha` 0.9–0.99 — the blue canvas would otherwise bleed through), wrapped half-Lambert diffuse with lavender-tinted shadows (`ambient 0.78`, `shadowTint`), a milky face-on frost (0.3), a rim-masked **nacre** thin-film hue drift (cosine palette on fresnel + `n.y` + `vWave`), and a cool cyan **bounce light** from below-left so it sits *in* the blue world. History below: it started as blue frosted glass.

**Sphere material (original notes)**: frosted glass (fresnel-driven alpha — transparent facing the camera, solid at the rim), not solid gloss. Built with a custom `ShaderMaterial`, not `MeshPhysicalMaterial` — no real refraction (nothing bends behind it), just alpha blending against the actual CSS background behind the canvas, which is enough to read as glass. True refraction would need a render-to-texture pass; flagged as a possible future upgrade, not started.

**Lighting for the physical-material shapes (current)**: `scene.environment` is a PMREM-prefiltered `RoomEnvironment` (`three/addons/environments/RoomEnvironment.js`, imported in parallel with three in `initHeroSphere()`, ~2KB chunk), `environmentIntensity 0.85`, plus the `keyLight` (2.2) and a weak ambient (0.25). Gyroscope rings (`#f6d9e6`), blocks (`#ece6f7`) and burst shards are pearl `MeshPhysicalMaterial` with `iridescence` — they were brand blue and read as navy silhouettes on the blue canvas. No tone mapping on the renderer, deliberately: it would shift the approved colours of the `MeshBasicMaterial` halo rings.

**Skills (gem) and Work (discs) are genuinely different objects, not sphere variants** *(paragraph describes the first designs — see the table above and the changelog for what's current)* — a flat-shaded `IcosahedronGeometry(1.05, 0).toNonIndexed()` and a stack of four `CylinderGeometry` discs respectively, both `MeshPhysicalMaterial` (clearcoat, no transmission — kept simple and reliable rather than chasing real refraction here too). They're lit by **real scene lights** (`keyLight` a `DirectionalLight`, plus one `AmbientLight`) added once near the top of `buildHeroSphere` — the only things in the scene that respond to real lights; the orb, rings, and bands all fake their own lighting inside their own shaders/materials and ignore `keyLight` entirely. `uGlobalAlpha` on the orb's shader cross-fades it out whenever `gem` or `discs` is active (`shapeSwap = min(1, gem + discs)`), so only one central object is ever visible at a time. The orbit rings and their markers are deliberately **not** part of that fade — they stay constant across every section regardless of which central object is showing, which is what makes the shape swap read as "the same stage, different exhibit" instead of a different scene entirely. Contact's beacon is the cheapest of the three: no new geometry, just a `uBeacon` uniform that adds a slow `sin(uTime)` pulse of soft light to the existing orb shader, strongest facing the camera rather than at the rim (so it doesn't compete with the glass fresnel sheen).

**Other sphere decorations, each independently driven by scroll state:**
- Two orbit rings with a moving marker + comet trail on each (`rings`, `ringDots`)
- Tech-stack text bands (`bandSide`, `bandTop`) — canvas-texture-based scrolling text, front/back faces handled separately so the back never shows mirrored lettering
- Ferrofluid spikes — vertex-shader lattice displacement (`spikeField`), independent of the (now-removed) tendril system below

**Background layers** (`.stage-wash`, `.stage-ambient`, `.stage-blob`, `.stage-grain`, all `position: fixed`, stacked by DOM order): a slow scroll-tied gradient wash (driven by `--scroll-progress` CSS var, set every frame in `tick()`), two drifting blurred blobs, and a JS-generated dithered noise texture (real per-pixel randomness, not SVG `feTurbulence` — the SVG version is still the CSS fallback if JS fails). The noise is intentionally light-biased (150–255 range) because it sits under `mix-blend-mode: multiply` — full-range noise there reads as harsh static, not film grain. Learned this the hard way; don't widen that range without re-checking against a screenshot.

**Other homepage mechanics:**
- `[data-scramble]` on section `h2`s — characters scramble through random glyphs then resolve left-to-right on scroll-into-view (`IntersectionObserver`, not GSAP). NOT applied to the hero `h1` — it has nested markup for the chromatic-lens hover effect that a `textContent` swap would break.
- `[data-magnetic]` on the five visible CTA buttons — pulls toward the cursor via `gsap.quickTo`. The navbar's own "Let's talk" link also has the attribute but is genuinely invisible at desktop widths (`lg:hidden` on its parent `<header>`, which is mobile-only since the sidebar took over) — don't be fooled by it into thinking magnetic buttons are broken; test against a visible one.
- Canvas fades in via `intro.opacity` (starts at 0, both in JS and as the CSS default on `.stage-canvas`) — masks the gap between page paint and the first WebGL frame actually landing.
- Motion-pause button stops the *ambient* animation (idle breathing, orbit spin) but scroll-driven response keeps working — intentional, not a bug.
- **Load choreography**: `initPageLoader()` sets a module-level `pageReady` promise (resolves when the loader starts fading, capped at 3s to match the CSS auto-hide). The hero copy (`[data-sphere-hero] [data-animate]`) starts hidden and rises in a stagger on it; the orb's `intro` tween waits on it too.
- **Scroll choreography** (`initScrollReveal()`): homepage `.stage-card`s enter from the side they sit on (`x ±90`, `rotationY ±9`, `expo.out`; plain rise below 1024px), then their children stagger in — `[data-stagger]` containers stagger per child. `[data-hero-content]` drifts up/dims (scrubbed) as you leave the hero.
- **`is-blue` class on `<html>`**: toggled by the curtain (`growP >= 1`). CSS uses it to flip the chapter rail, caption and card borders to light-on-blue.
- **Chapter rail** has a progress hairline (`.chapter-rail__track::after`, `scaleY(var(--scroll-progress))`) and a bead beside the current chapter. The bottom caption doubles as the **scroll cue** in the hero (`.is-cue`, hero waypoint caption is "Scroll to explore").
- **Light-dust field** (`dust`, `THREE.Points`, 720 desktop / 260 compact): all motion in the vertex shader (scroll parallax by depth, idle drift, pointer offset); `uAlpha = dustPresence` = the curtain's `reappearP`, so it only exists on the blue canvas.
- **Orb hover**: per-frame ray-vs-bounding-sphere test (cached `canvasRect`, desktop only, only while `uGlobalAlpha > 0.6`) → `orbHover` adds distortion + spin; toggles `#cursor-ring.is-orb`.
- **Sidebar scroll-spy** (`initSectionSpy()`, IntersectionObserver, works under reduced motion): `[data-spy]` links + one sliding `[data-sidebar-indicator]` bar; falls back to the `aria-current="page"` route link on Work/Blog.
- **Footer**: velocity-reactive marquee (`initMarquees()`, Lenis velocity → boost + direction, wraps at -50%, only ticks on screen), live IST clock (`initLocalTime()`, server-rendered first), back-to-top (`initBackToTop()`).
- **Cards**: cursor spotlight (`initCardSpotlight()` feeds `--spot-x/y`; `--spot-o` is an `@property` so it can transition).

## Current state — shared layout & other pages

The ambient background (`.stage-wash`, `.stage-ambient`, `.stage-blob` ×2, `.stage-grain`) now lives in `layouts/app.blade.php`, not `home.blade.php` — it renders on **every** page. The sphere canvas lives there too, gated behind `@if (request()->routeIs('home'))`, so it only ever mounts on the homepage.

**Why the canvas had to move, not just get an `@if`:** `<main>` has `position: relative; z-index: 10`, which creates its own stacking context. Early on, the canvas sat inside `@section('content')` (i.e. inside `<main>`) while the other four background layers sat in the layout (i.e. direct children of `<body>`, outside `<main>`'s context). That split the five layers across two different stacking contexts — the canvas, promoted to `<main>`'s z-index:10 context, would have painted *above* the grain instead of under it, even though their own CSS all says `z-index: 0`. Fixed by keeping all five as true siblings outside `<main>`. If the sphere ever needs to render somewhere nested again, re-check this — z-index numbers on the elements themselves don't matter if an ancestor has already put them in different stacking contexts.

`projects/index.blade.php` (Work), `projects/show.blade.php` (case study), and `contact.blade.php` now share the homepage's visual language: `.stage-section` padding, the `.stage-card` / `.stage-card--wide` glass-panel treatment (wide variant added for these — the base 34rem is sized for the homepage's alternating-card layout, too narrow for a form or a full case study), `data-scramble` on their `h1`s, `data-magnetic` on their primary CTAs, and the shared `.tag-pill` class for every tag/tech-stack chip site-wide (previously three different ad hoc pill stylings across home/project-card/show). Sidebar nav now shows an active-page highlight (`request()->routeIs('work.*')` etc.) and a hover micro-interaction (slight translate + tint) on every link, not just a color change.

Cross-document **view transitions** are on (`@view-transition { navigation: auto; }` in `app.css`) — a plain cross-fade between any two pages on the site, no JS. No-ops silently in browsers that don't support it yet (Safari, older Firefox); nothing to maintain there.

## Changelog

**2026-10-06 — "Professional level" pass: scroll choreography, 3D quality, new components, three real bugs** — User asked to make the site professional "from scrolling effect to 3D animation" and to add top-tier components. Audited first with settled-position screenshots at every section, which surfaced three genuine bugs before any design work:
1. **Blue triangular holes in the resting Contact orb.** Contact rests at `x = -1.55`, so raw `crossing` idled at ~0.03 — enough to keep the burst shards "visible" at ~3% opacity, and since `fragmentMaterial` wrote depth, each near-invisible shard punched a hole through the orb drawn after it. Fixed twice over: `depthWrite: false` on the shards (same lesson as the gem/discs fade), and `explodeAmount = smoothstep(crossing, 0.08, 0.9)` so true rest is exactly 0.
2. **About's orb was ~50% transparent while you read About.** The curtain's 900px timeline spread the orb's return over its whole second half, so with About centred (scrollY ≈ 667 at 900px tall) `heroWipeDissolve` was still ~0.5 — a washed-out lavender ghost. Now `end: '+=700'` with the return finishing at 85% (`reappearP = (p - 0.5) / 0.35`).
3. **Any `ScrollTrigger.refresh()` could switch the whole blue world off** (latent since the `scrollY > 0` idle gate was added; the new accordion exposed it). GSAP's `_refreshAll` literally scrolls to 0, updates triggers, then restores scroll — our onUpdate saw `scrollY === 0` mid-refresh, applied the idle state, and never re-fired because progress ended where it started. Window resizes and the fonts-ready refresh could hit it too. Fixed: onUpdate ignores calls while `ScrollTrigger.isRefreshing`, and a `ScrollTrigger.addEventListener('refresh', …)` re-applies the real state (`applyCurtain(realProgress(curtain))`). Verified after an accordion toggle, after a viewport resize inside the blue zone, and on a `/#skills` hash load.

**Fixed: loading the page with a URL hash left everything in a stuck, half-resolved state** — User loaded `/#skills` directly and got a broken-looking mix of hero content, a frozen half-grown blue wipe curtain, and a half-positioned sphere all at once. Root cause pre-dates the wipe curtain — it just made an existing gap dramatically visible: `initNav()`'s click handler only ever intercepted *same-page* anchor clicks (explicitly bails if `url.pathname !== window.location.pathname`); a fresh load with a hash already in the URL (a cross-page nav link — the sidebar's About/Services/Skills links are literally `route('home').'#skills'` — a bookmark, a shared link, back/forward) was left entirely to the browser's own native instant jump-to-fragment, which races against Lenis/GSAP/the sphere system still initialising. Each system ends up reacting to a different transient scroll value mid-race.
Fixed in `app.js`: (1) `history.scrollRestoration = 'manual'` plus an immediate `window.scrollTo(0, 0)` right at the top of the module (before anything else runs) neutralises the browser's native jump; (2) a new `resolveInitialHash()`, called once in `DOMContentLoaded` right after `initSmoothScroll()` so `lenis` already exists, explicitly jumps to the hash target via `lenis.scrollTo(target, { immediate: true, offset: -16 })` (falling back to plain `scrollIntoView` if `lenis` is null, i.e. `prefersReducedMotion`). This makes it the *one* coordinated path every scroll-driven system observes, instead of a native jump none of them know about. Verified via Playwright: direct load of `/#skills` lands cleanly on the gem with no stuck curtain and no hero bleed-through, both immediately and after settling; plain `/` load is unaffected (still starts at scrollY 0); same-page sidebar nav clicks still animate via Lenis exactly as before. Zero console errors.

**Redesigned the opening curtain: blue becomes About's actual background, not a dissolve-away overlay** — User refined the original curtain concept after seeing it: idle should be fully hidden, a modest scroll should trigger quick growth, and — the real change — it should *hold* as the literal page background for the whole About section (content rendering on top of it) rather than covering the frame and immediately dissolving away to reveal the old light theme underneath. Split the single ScrollTrigger into two independent ones in `app.js`, because the two things they drive have no reason to share a timeline:
- **Grow** (`trigger: '#about', start: 'top 95%', end: '+=450'`): a *fixed* 450px of scroll, deliberately not proportional to anything about About's own height — "scrolling a bit" shouldn't depend on how tall a section happens to be. Also toggles the curtain's own `z-index` (50 while growing, so it still covers the hero text; drops to 5 — below `<main>`'s z-10, above the other z:0 background layers — the instant it finishes), which is what actually makes "content continues on the blue canvas" work: About's card was rendering normally in `<main>` the whole time, it just couldn't be seen above the opaque z-50 layer until that drops away.
- **Fade** (`trigger: '#services', start: 'top 90%', end: 'top 20%'`): tracks the *next* section's approach, not About's own bottom edge. First attempt used About's bottom (`'bottom 85%'`) and fired far too early — About (sized to content, ~600px) is shorter than the viewport (1000px), so its bottom edge crosses any given viewport percentage almost as soon as its top does. Tracking where Services enters, regardless of how tall About is, is what actually means "right as the handoff happens" — same lesson as the grow trigger's fixed-pixel-distance choice, from the opposite direction.
Between the two triggers' active ranges, *nothing* touches the curtain's styles — that's the hold, achieved by omission rather than a third explicit state. `heroWipeDissolve` (the orb's visibility, via `uGlobalAlpha`) is irrelevant during the hold since the orb is invisible behind the opaque curtain regardless — it only needs to track the fade trigger's second half to restore the orb in time for Services' own effects, which it already did from the previous round of fixes.

**Fixed: faint blue circle visible at true idle** — User spotted a small faint blue circle sitting near the hero orb before any scrolling happened. Root cause: GSAP fires a ScrollTrigger's `onUpdate` synchronously once at `.create()` time, before fonts/layout/the hero's own intro animation have necessarily settled — that premature call measured a small non-zero progress (observed: opacity `0.067`, a real ~85px circle) even though the actual scroll position was 0, and since scrub `onUpdate` only re-fires on real scroll events, that faint leftover state just sat there indefinitely at idle. Fixed in `app.js` by forcing `p = window.scrollY > 0 ? self.progress : 0` inside the curtain's `onUpdate` — sidesteps the quirk entirely rather than chasing GSAP's exact internal timing: regardless of what it measured before the page settled, true idle (`scrollY === 0`) now always renders the clean zero state. Verified across three fresh page loads with `getComputedStyle` — consistently `opacity: 0`, `clip-path: circle(0px ...)`.

**Richer left-right crossing arc, not just "small then big"** — User felt the crossing transform (built two rounds ago) read as just a scale pulse. Reworked the same `crossing`/`travelRemaining`-driven formulas in `tick()`: `arcDepth` roughly doubled (-0.5 → -1.1) so real perspective falloff — the camera is genuinely farther from the object — does more of the apparent-shrink work, while `arcScale`'s artificial multiplier shrank correspondingly (12% → 7%) so it's topping up a natural effect rather than carrying it alone; added `arcLift` (a vertical bump added to `sphere.position.y`, peaking at the crossing's midpoint) so it traces an actual arc/swing trajectory instead of sliding flat and just resizing in place; and added `tumble` (yaw, `rotation.y`) and `pitch` (`rotation.x`, derived from `bank`) alongside the existing `bank` (roll, `rotation.z`) — a three-axis tumble reads as genuinely three-dimensional where a lone z-roll reads flat. All of it still scales off the same `crossing`/`travelRemaining` values as before, so it dissolves to exactly 0 at rest with no new fade-out logic needed. Verified by temporarily exposing the sphere group on `window.__debugSphere` (removed before finishing — same debug-and-remove pattern used earlier in this file) and logging position/scale/rotation across two different section crossings: confirmed real multi-axis rotation and a genuine y-lift at the crossing peak, not just the scale change, then visually confirmed via screenshots.

**Squash-and-stretch on the orb during left-right crossings** — User asked what would make the crossing feel more natural; squash-and-stretch (one of animation's classic principles) was the suggestion, since the orb's shape stayed rigid through the whole arc (shrinking/rotating uniformly) while everything else about the motion had gotten more physical. Added a `stretch` factor (`crossing * 0.22`) applied via `sphereMesh.scale.set(1 + stretch, 1 - stretch * 0.5, 1 - stretch * 0.5)` — elongated along local x, compressed on y/z by half as much each (a volume-preserving-ish ratio), peaking at the same mid-crossing moment as the depth/lift/tumble already there.
Deliberately applied to `sphereMesh` directly, **not** the parent `sphere` group that the existing `arcScale` uses — the group also carries the gem, discs, bands, and rings, and a non-uniform *group* scale would smear the gem's hard facets and the discs' crisp edges into a distorted ellipsoid whenever a shape-swap happens to overlap a crossing (gem/discs fade in/out based on scroll position independently of the crossing, so the two can coincide near a section boundary). The blobby orb is the only thing in this scene that reads as organic under non-uniform scale; the faceted/geometric shapes would just look broken.
Verified by temporarily exposing `sphereMesh` on `window.__debugSphereMesh` (removed before finishing): confirmed scale sits at exactly `(1, 1, 1)` at rest and ramps smoothly up to roughly `(1.18, 0.91, 0.91)` at the crossing peak then back down, and visually confirmed the orb reads as a soft, elongated object mid-flight rather than a rigid shape that merely shrinks. Zero console errors across a full scroll sweep; idle state (from the previous fix) still clean.

**Explode-and-rebuild crossing, plus halo ring tilt + mood sync** — User asked for a more creative/believable left-right crossing and explicitly asked for "explode, then rebuild on the next section." Important context surfaced before building: a full explode-into-fragments-then-reassemble system was built earlier in this project and explicitly reverted (per the changelog entry above) — the gem/discs/beacon shapes were deliberately built afterward as "one continuous mesh per section, not a particle swarm" specifically because of that revert. Flagged this to the user with options (lightweight particle burst / shader-only shatter / full fragment mesh); they picked full fragment mesh anyway, so built it — but scoped meaningfully differently from the reverted version:
- The reverted system made each **section's resting identity** a reassembled shape (data-driven node counts per section, continuous `scrollCurrent.form` value). This version only ever exists **during the crossing itself** — shards always explode out of and collapse back into a plain sphere, driven by the same `crossing` value (peaks at horizontal centre, 0 at rest) the arc/tumble/stretch work already uses. It has no idea what Skills or Work or Contact look like; it doesn't need to.
- `FRAGMENT_COUNT = 48` `InstancedMesh` of small tetrahedra (`THREE.TetrahedronGeometry`), each with a fixed random "assembled" direction that doubles as its explode direction (a radial burst reads as "this shape flew apart," not a random scatter) plus a random spin axis/speed for tumbling as they separate. Whichever shape would otherwise be showing — orb (`uGlobalAlpha`), gem, or discs — gets multiplicatively dissolved by `(1 - crossing)` in the same frame, so the shards read as having taken that shape's place rather than sitting on top of it.
- Verified visually across two different crossings (hero→About, and the richer Services→Skills→Work region where gem/discs fades overlap the explosion) — reads as a deliberate, legible burst-and-reform even when layered with an in-progress shape-swap, not visual noise. Zero console errors across a full scroll sweep; idle state still clean.

**Fixed broken gem/discs transition (floating-shard artifact)** — The gem (Skills) and discs (Work) were visibly breaking apart into scattered floating triangle shards mid-fade, reported by the user with screenshots and reproduced exactly via a fine-grained Playwright scroll scrub (0.15 viewport-height steps through each handoff). Root cause: `gemMaterial`/`discMaterial` are `transparent: true` with the Three.js default `depthWrite: true` — on a flat-shaded, non-indexed mesh (or a stack of several overlapping discs), there's no guaranteed back-to-front triangle draw order, so whichever facet rasterises first writes depth and blocks/overwrites others unpredictably once opacity is partial. At full opacity (steady state, e.g. the final Skills/Work screenshots) this was invisible; it only showed up *during* the cross-fade, which is why earlier verification (full-section screenshots only) missed it.
